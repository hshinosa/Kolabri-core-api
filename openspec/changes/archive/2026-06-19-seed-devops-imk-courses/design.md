## Context

The demo seed is dual-write: `seed-demo-data.ts` (core-api, PostgreSQL+Mongo) defines courses, weeks, and material metadata; `MaterialsDemoSeeder.php` (client-app, MySQL) fetches the course list from core-api (`/api/courses/my`) and generates the PDF files + MySQL metadata. Both use a shared `seedUuid("<key>")` so IDs match across databases.

Currently `COURSES` (core-api) and `$courseWeeks` (client-app) only enumerate IF201–IF212. DEVOPS102 and IMK401 exist on the deployment because a lecturer created them by hand after seeding; their UUIDs are random and they have PDFs on disk (generated by the client-app fallback branch) but no PostgreSQL material metadata.

## Goals / Non-Goals

**Goals:**
- Make the seed enumerate all 14 courses so a reset reproduces the deployed catalog.
- Keep PDF filenames identical to what is already on disk (avoid orphaned files / needless regeneration).
- Deterministic, cross-database UUIDs via `seedUuid`.

**Non-Goals:**
- Migrating the existing live UUIDs in place (they are random; a re-seed replaces them deterministically — accepted, see Risks).
- Changing the dual-write architecture (the AGENTS.md "single source of truth" refactor is out of scope).
- Any runtime/API change.

## Decisions

**D1 — Add full `CourseContent` entries, not stubs.**
Match the richness of the existing 12 (topics, assignmentQuestions, hotDiscussions, aiPrompts, aiResponses, goals, reflections) so seeded discussions/goals/reflections for the two courses are realistic. Stub entries would produce empty or generic demo data inconsistent with the rest.

**D2 — Week/material titles chosen to reproduce existing PDF filenames.**
The client-app PDF filename is `Str::slug("{code} {topic}")`. The on-disk PDFs are `devops102-pengantar-devops`, `-fundamental-devops`, `-analisis-kasus-devops`, `-latihan-devops`, `-perancangan-proyek`, `-implementasi-evaluasi` (and the IMK401 analogues). The explicit `$courseWeeks` / `COURSE_WEEK_DATA` entries use the exact material names that slugify to those filenames, so existing PDFs are reused, not orphaned. Alternative (fresh themed names) rejected: would regenerate PDFs and strand the current files.

**D3 — Accept deterministic-UUID cutover for the two courses.**
After re-seed, DEVOPS102/IMK401 get `seedUuid("course-DEVOPS102")` / `…IMK401`, replacing the random live UUIDs. RAG collections must be re-ingested under the new UUIDs. This is a one-time, documented operational step; the live deployment keeps working until the operator chooses to re-seed.

## Risks / Trade-offs

- [Re-seed changes the two courses' UUIDs → old Qdrant collections (3796dad2…, 9bdb4f98…) become stale] → Tasks include deleting the stale UUID collections and re-ingesting under the new deterministic UUIDs; ingest is idempotent per `file_id`.
- [Core-api `COURSE_WEEK_DATA` and client-app `$courseWeeks` drift] → Keep both edits in the same change; the spec requires identical week/material titles across the two seeders (the existing 12 already satisfy this).
- [Owner/lecturer assignment] → The two courses follow the existing `lecturers[i % lecturers.length]` round-robin; no special handling.

## Migration Plan

1. Edit `seed-demo-data.ts` (`COURSES` + `COURSE_WEEK_DATA`) and `MaterialsDemoSeeder.php` (`$courseWeeks`).
2. Local dry validation: `npx tsc --noEmit` (core-api), `php -l` (client-app seeder).
3. On a target environment, re-seed: `npm run db:reset:demo-data` then client-app `php artisan db:seed --class=MaterialsDemoSeeder` (or `./scripts/seed-demo.sh`).
4. Re-ingest RAG for the two courses under their new deterministic UUIDs; delete the stale random-UUID collections.
5. Rollback: revert the two source edits; prior random-UUID courses can be re-created manually if needed (or restored from backup).
